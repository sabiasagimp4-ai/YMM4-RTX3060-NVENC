## 2. 不具合と、キャッシュが効かなくなる問題

### 2.1（#1）描画に関係しない設定の変更で、キャッシュの依存状態が全部無効になる

**内容**
`KeyDependencyTracker` は `YMMSettings` 全体の `PropertyChanged` を購読し、どのプロパティが変わってもプロジェクト全体を無効にする（`KeyDependencyTracker.cs:449`、`:504-507`）。一方、キーに入る `YMMSettings` の値は `ZoomMode`、`MFSourceReaderMode2`、`VoiceUpsamplingMode` の 3 つだけ（`FrameCacheKey.cs:226-228`）。

**本体で確認**
`YMMSettings.TimelineZoom` を 100 → 151 にすると `PropertyChanged` が来て、取得済みのキーが無効になった（revision 0 → 2）。`YMMSettings` には描画に関係しない UI の状態が多い。例：`TimelineZoom`、`LayerHeight`、`Volume`、`IsMuted`、`PlaybackRate`、`IsRepeatPlayEnabled`、`CollapsedEditorGroups`、`DockingLayout`、`ToolStates`、`MainWindowStates`、`UIScale`。

**影響**
- 変更から 250 ms は全フレームが通常描画になる（`SettleMilliseconds`）。ズームのように続けて変わる操作では、その間ずっと続く。
- その後、プロジェクト全体の記述（JSON 化・分割・ハッシュ）をやり直す。200 アイテム以下なら描画スレッドで行う（`DescribeInline`）。再生中なら、そこでコマ落ちし得る。
- 保存済みのフレームは残る。キーは内容から作るので、記述し直せば同じキーになる。
- 停止中の先読みは中断し、巡回位置が先頭に戻る（`IdleFramePreRenderer.Session.OnInvalidated`）。

**直し方**
`YMMSettings` からの通知は、キーに入るプロパティ（`ZoomMode`、`MFSourceReaderMode2`、`VoiceUpsamplingMode`）の名前のときだけ無効にする。2 回目の検査で、描画のコードが読む `YMMSettings` のプロパティは他に無いことを確かめた。

**確認方法**
CacheChecks に「`TimelineZoom` を変えてもキャプチャが有効なまま」「`ZoomMode` を変えると無効になる」を追加する。

### 2.2（#2）レイヤーの名前・色・音量を変えると、保存済みの全フレームが使えなくなる

**内容**
キーの「全フレーム共通」の部分に、ルートのタイムラインの `LayerSettings` が丸ごと入る（`FrameCacheKey.cs:223`、`FrameModelSplit.cs` の Global）。本体で `LayerSettings` の中身を確かめると、レイヤーごとに `Label`（名前）、`Color`（タイムライン上の色）、`IsHidden`（非表示）、`Volume`（音量）を持っていた。

**影響**
- 名前と色はタイムラインの表示用で、描画には効かないと考えられる。描画に効くのは `IsHidden`。`Volume` は音声を読むフレーム（シーンアイテム・音声波形）にだけ効く。
- それでも、名前や色を変えると全フレームのキーが変わる。保存済みのフレームは RAM・ディスクに残るが、二度と使われない。
- 描き直しが終わるまで、プレビューは通常描画になる。停止中の先読みも先頭からやり直しになる。

**直し方**
- `Label` と `Color` を記述から外す。
- `Volume` は wide なフレーム（音声を読むフレーム）の部分へ移す。
- `IsHidden` は今のまま共通部分に置く。そのレイヤーのアイテムを含むフレームだけに限ることもできるが、後回しでよい。

**確かめたこと（2 回目の検査）**
本体のどのコードがどの設定を読むかを全部洗い出した。描画のコードが読む設定は、フォント設定（`FontSettings`）とファイル種別（`FileSettings.FileExtensions`）だけだった。どちらもキーに入っている。「設定を変えても古い絵が出る」問題は見つからなかった（§5）。

### 2.3（#3）検証できない場所の素材を使うフレームは、一切キャッシュされない

**内容**
フレームが使う素材は、毎回「リンクを含まないローカル固定ドライブ上の NTFS の通常ファイル」であることを確かめ、内容の SHA-256 を指紋にする。次の素材は検証に失敗し、そのフレームは常に通常描画になる。

| 素材の場所・種類 | 失敗する箇所 |
| --- | --- |
| 親フォルダーを含めて reparse point を持つもの（OneDrive の同期フォルダー、シンボリックリンク、ジャンクション） | `FileDependencyLease.cs:52`（`IsLocalPlainFile`）、`:173-181` |
| exFAT・FAT32 のドライブ（USB メモリ、外付け SSD に多い）、ReFS | `:56`（`IsNtfsVolume`） |
| ネットワークドライブ・NAS | `:177`（`DriveType.Fixed` 以外） |
| 4 GiB を超えるファイル（長い録画） | `:68`、上限は `KeyDependencyTracker.cs:10` |

**影響**
- 素材をどこに置くかで、キャッシュがほとんど効かなくなる。
- ゆっくり動画では、ほぼ全フレームにボイスアイテムがある。ボイスの音声ファイルもフレームの依存に入る（`FrameCacheKey.cs:168`）。
- このため、ボイスの保存先が OneDrive 配下（「ドキュメント」や「デスクトップ」のバックアップを有効にした Windows）だと、字幕の出るフレームがすべて対象外になる可能性がある。
- 4 GiB は、OBS の 1080p60（約 20 Mbps）なら約 30 分の録画に当たる。

**確度**
- 失敗する箇所：コードで確認。
- OneDrive の同期済みファイルが reparse point を持つか：要実機確認。Cloud Files の placeholder は同期済みでも reparse point のまま、と理解している。
  - 確認方法：PowerShell で `(Get-Item '<素材のパス>').Attributes` を実行し、`ReparsePoint` が含まれるか見る。
  - または、ツール「描画キャッシュ」の状態欄に「外部素材の一部を検証できません」と出るか見る。

**直し方（案）**
- 4 GiB 超：指紋を「全内容の SHA-256」から変える。例：ファイル ID・サイズ・更新時刻・変更時刻をキーにした指紋の永続化（前回の C3）。または先頭・末尾・等間隔の部分ハッシュとサイズの組み合わせ。安全性の前提が変わるため設計判断が要る。
- OneDrive：reparse tag が Cloud Files（`IO_REPARSE_TAG_CLOUD_*`）で、`FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS` が無い（ローカルにある）ものだけを許す。パスの別名検出は別の方法で保つ。
- exFAT：ファイル ID が安定しないため、そのまま許すのは危険。指紋の方式を変えるときに一緒に検討する。

### 2.4（#4）3 のフレームに来ると、停止中の先読みが永久に止まる

**内容**
idle のバッチは、キーを作れないフレームに来ると、そのフレームを「恒久的に通常描画」とみなさない限り、そこで止まる。
- 先頭フレーム探し：`IdleFramePreRenderer.cs:235-246`。`TryCapture` が失敗し、`RendersNormally` が false。
- 途中：`:280-282`。`IdleFrameResult.NotKeyed`。

どちらも巡回位置を進めずに戻る（`Advance` を呼ばない）。`RendersNormally` が true になるのは、記述の時点で対象外と分かるもの（立ち絵・外部プラグイン・解決できないフォント）、ID で乱数を作るもの、起動後に上書きされた素材だけ（`KeyDependencyTracker.cs:90-96`）。2.3 の失敗はどれにも当たらない。

**影響**
- 次のタイマー（250 ms 後）で同じフレームから再開し、また止まる。そのフレームより先は先読みされない。
- 状態欄には検証できない理由が出続ける。
- [CACHE_BEHAVIOR.md](CACHE_BEHAVIOR.md) の「保存できなかったフレームを無期限に再試行するものではない」と食い違う。

**直し方**
理由が一時的なもの（「準備中」「背景で検査中」「編集中」）なら止まる。それ以外（検証失敗）なら飛ばして先へ進む。理由の文字列ではなく、`TryCapture` から理由の種類を返すようにする。

**確認方法**
IdleFramePreRendererChecks に、exFAT 相当（検証が失敗する）素材を使うフレームの後ろにある通常のフレームが先読みされるテストを足す。テストではファイル属性の検査を差し替える。

### 2.5（#6）取り消した・失敗した NVENC 出力の途中ファイルが残る

**内容**
NVENC 出力は、出力先と同じフォルダーの `.名前.mp4.<GUID>.partial` に書き、成功したときだけ本来の名前へ移す（`NvencVideoFileWriter.cs:30-31`、`:186-189`）。取消・失敗・フレーム数の不一致では移さないが、消しもしない。ネイティブ側も消さない（`NvencNative.cpp` の `NvencDestroy` は閉じるだけ。`DeleteFile` の呼び出しは無い）。

**影響**
取り消すたびに、途中までの MP4 が GUID 付きの別名で出力先に残る。長い動画では 1 本で数 GB になる。名前の先頭が `.` でも、Windows では隠しファイルにならない。

**直し方**
`DisposeCore` の最後で、移さなかった場合は `NvencDestroy` の後（ファイルが閉じた後）に `_stagingPath` を消す。デバッグログ（`.partial.nvenc_log.txt`）は残す。

**確認方法**
ManagedSmoke か NativeSmoke に、取消したときに `.partial` が残らないテストを足す。NVENC が無い CI でも、エンコーダーを作る前の取消は確かめられる。

### 2.6（#7）NVENC 出力の設定が保存されない

**内容**
出力設定は `NvencVideoFileWriterPlugin` の通常のフィールド（`new NvencSettings()`、`NvencVideoFileWriterPlugin.cs:13`）にあり、`SettingsBase` ではない。

**影響**
YMM4 を起動し直すたびに、H.264・12000 kbps・YouTube 推奨・標準に戻る。H.265 や固定ビットレートで出したい人は、毎回選び直す必要がある。

**直し方**
`FrameCacheToolSettings` と同じように `SettingsBase` の設定クラスにして、変更時に保存する。

## 3. 出力品質と使い勝手

### 3.1（#5）NVENC 出力が色空間を書いていない

**内容**
- フレームは BGRA（ARGB）のまま NVENC に渡し、YUV への変換は NVENC 内部で行う（`NvencVideoFileWriter.cs:288-298`）。
- ビットストリームの VUI（`videoSignalTypePresentFlag`、`colourMatrix` など）も、MP4 の `colr` ボックスも書いていない（`NvencNative.cpp` に該当する設定が無い）。

**根拠**
FFmpeg の NVENC 実装は、RGB を入力にするとき `colourMatrix` を BT.601（`AVCOL_SPC_BT470BG`）、範囲を limited と明示している（[libavcodec/nvenc.c](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/nvenc.c)）。NVENC 内部の変換は BT.601 と考えられる。

**影響（要実機確認）**
色空間の指定が無い HD 動画を、多くのプレーヤーやブラウザ、YouTube は BT.709 として表示する。BT.601 で変換して BT.709 として表示されると、彩度の高い赤・緑・青の色味がずれる。ゆっくり動画の、彩度の高い文字や背景で目に付く可能性がある。

**直し方**
H.264/H.265 の VUI に `colourMatrix = BT.601`（SMPTE 170M）、`colourPrimaries = BT.709`、`transferCharacteristics = BT.709`（または sRGB）、`videoFullRangeFlag = 0` を書く。BT.709 で出したい場合は、既にある VideoProcessor の NV12 変換経路で色空間を BT.709 に設定して使う。

**確認方法**
1. 純色（赤・緑・青・肌色）のカラーバーを NVENC 出力する。
2. `ffprobe -show_streams` で `color_space` が `unknown` か確かめる。
3. ブラウザで再生した画面と、YMM4 のプレビューを並べて比べる。

### 3.2（#8）停止中の先読みは「描画キャッシュ」ツールを開いている間しか動かない

**内容**
先読みが使うタイムラインは、ツールの ViewModel の `SetTimelineToolInfo` からしか渡されない。ツールを閉じると `ClearTimelineToolInfo` で外れる（`FrameCacheTool.cs:108-109`）。

**影響**
README は「停止中は操作から既定 8 秒後にタイムライン全体を先読みします」とだけ書いている。ツールを閉じている人には、先読みが動かない理由が分からない。

**直し方**
- 少なくとも README と設定画面に書く。
- できれば、プレビュー（`TimelineVideoPlayer`）から得たシーンを使って、ツールを開いていなくても動くようにする。

### 3.3（#11）素材ファイルを他のアプリから上書きできない時間がある

**内容**
フレームの検証は、使う素材を `FileShare.Read`（書込・削除・名前変更を拒否）で開いたまま保持する（`FileDependencyLease.cs:53`）。
- 再生中は、保存待ちの読み戻し（最大 3 枚）と現在のフレームの分、ほぼ常に開いている。
- 背景の指紋計算は、最大 128 ファイルを開いたまま順にハッシュする（`KeyDependencyTracker.cs:405-413`）。大きな動画が混じると数十秒になる。

**影響**
その間、画像編集ソフトやボイス生成ソフトで素材を上書き保存すると、共有違反で失敗し得る。

**直し方**
指紋計算はファイルごとに開いて閉じる。ハッシュ中のファイル以外を開いたままにしない。再生中の保持は設計上必要（上書き検出の前提）なので、状態欄に「再生中は素材を上書きできない」と出す程度にとどめる。

### 3.4 出力品質の余地（不具合ではない）

- B フレーム（`frameIntervalP = 1`）、lookahead、AQ を使っていない（`NvencNative.cpp` の `InitializeEncoder`）。同じビットレートで画質を上げる余地がある。
  - B フレームを使うには、MP4 に `ctts`（表示順のずれ）を書く必要がある。今の MP4 書き出しには無い。
- `moov` をファイルの末尾に書く。ブラウザでの途中再生やアップロード前のプレビューで、先頭から再生できるまで待たされることがある。

## 4. 性能と小さな問題

### 4.1（#9）検証できない素材があると、5 秒ごとに全素材を開き直す

**内容**
指紋が揃わないフレームの検証が来るたびに、前回の失敗から 5 秒経っていれば指紋計算をやり直す（`KeyDependencyTracker.cs:198-205`、`:303-307`）。やり直しはプロジェクトの全素材が対象で、変わっていない素材もすべて開いてスタンプを読む（ハッシュは前回の値を使う）。キャッシュの帯（250 ms ごと）や先読みからも始まる（`:285`）。

**影響**
2.3 の素材が 1 つでもあると、再生中・停止中を問わず 5 秒ごとに全素材を開き直す。素材が数百あると、ウイルス対策のスキャンを含めて目に見える背景 I/O になり得る（要計測）。

**直し方**
失敗したファイルを、そのスタンプ（ファイル ID・サイズ・時刻）と一緒に記憶する。スタンプが変わるまで再検証しない。

### 4.2（#10）再起動後のディスクキャッシュの追い出し順

**内容**
起動時の索引の読み込みは、ディレクトリを列挙した順に LRU の末尾へ入れる（`FrameCacheStore.cs:695`）。NTFS の列挙順はファイル名（キーのハッシュ）順で、使った順ではない。

**影響**
再起動後に容量（4 GiB）が一杯になると、最近使ったフレームから消えることがある。

**直し方**
列挙したファイルを最終書込時刻（または読込時に更新する時刻）で並べてから LRU に入れる。

### 4.3 その他（小さい）

- **起動直後の待ち**：起動直後、ディスクの索引を読み込む間（4096 ファイルのヘッダーを読む）、一時停止中の未保存フレームごとに最大 50 ms 待つ。読込キューが一杯になる（128 件）まで続く（`FrameCacheStore.cs:166-170`）。索引が無い間は待たない方がよい。
- **出力の失敗が無言**：フレーム数が合わない出力は、エラーを出さずにファイルを作らない（`NvencVideoFileWriter.cs:150-151`、`:184-185`）。本体の範囲の計算はプラグインと同じことを確認した（§5）ので、起きる条件は限られる。それでも、取消でないのに合わないときは例外にして理由を出す方がよい。
- **GPU 予算が固定**：画像の総予約は 384 MiB で固定（`TimelineFrameCache.cs:30`）。4K のプレビュー（1 枚 33 MB）では、保存待ち 3 枚・表示中・プール・GPU 保持を合わせて予算を超え、保存を見送ることがある。RTX 3060（12 GB）には小さすぎる。前回の C1（VRAM の予算を実測）で扱う。
- **プールがデバイスを区別しない**：読み戻し用のテクスチャのプールは、大きさと形式で使い回す。作ったデバイスは見ていない（`TimelineFrameCache.Readback.cs:428-432`）。デバイスロスの後も同じソースが使われ続けると、別のデバイスのテクスチャで失敗し続ける（保存されないだけで、表示は壊れない）。形にデバイスのポインターを含めると防げる。
- **キャッシュの帯**：変化が無くても 250 ms ごとに全区間を照会し、ストアのロックを握る（前回の「その他」と同じ）。ストアの `Version` とビューが変わらなければ省ける。
- **先読みはアプリが背面でも全力で動く**：YMM4 への入力だけを見ているので、他のアプリで作業中（ゲームや録画を含む）も、8 秒後から GPU・CPU・ディスクを使う。AE と同じ考え方とも言えるので、仕様として決める。
- **ドキュメントが古い**：[CACHE_BEHAVIOR.md](CACHE_BEHAVIOR.md) は、読み戻しの保留を「各 source で 1 枚まで」と書いていた。前回 3 枚に変えたので、この調査で直した。
