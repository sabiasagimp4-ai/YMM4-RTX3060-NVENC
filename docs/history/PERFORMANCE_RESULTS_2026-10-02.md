## 2. 測定条件と読み方

### 2.1 何を測ったか

- **ホストと解像度**：YMM4 Lite 4.56.1.0 の実 DLL、1920×1080、30 fps、100 フレーム。
- **1 フレームの時間**：1 フレームの `TimelineSource.Update` ＋ `Draw` を、テストの描画スレッドで計った時間です。GUI の表示 FPS、Present、音声は含みません。
- **2 種類のプロジェクト（fixture）**
  - `base`：毎フレーム図形 1 個と Arial のテキスト。依存ファイルは Arial のフォント 5 ファイルです。
  - `files24`：`base` の内容に図形 120 個と、別々の WAV を持つ音声アイテム 24 個を加えたもの。依存ファイルは 1 フレーム 29 個です。
- **キャッシュ状態**：GPU hit、RAM hit、未キャッシュで保存まで行う cold-store、キャッシュ OFF の off。

### 2.2 ランナーの速さの違い

## 5. 悪化・副作用

### 5.1 1 回目の再生で保存できる枚数が減った

| ケース | 修正前 | 修正後（1 回目 / 2 回目） |
| --- | --- | --- |
| base cold-store | 100 / 100 枚 | 86 / 94 枚 |
| files24 cold-store | 100 / 100 枚 | 96 / 99 枚 |

非待機 readback は、GPU の読み戻しが次のフレームまでに終わらないと、そのフレームの保存を見送る設計です（`readback-busy`）。フレームが速く回るようになり、WARP では GPU の処理が CPU の 2 コアを共有するので、見送りが増えたと考えています。ただし、この CI ログには見送り理由の内訳が出ないため、確認はできていません。

見送ったフレームは通常どおり描画・表示されます。保存は 2 回目以降の再生か idle で行われます。表示が間違う方向の問題ではありませんが、1 回目の再生で埋まる量は減ります。RTX 3060 では読み戻しがずっと速いので影響は小さいと見込みますが、未確認です。

### 5.2 idle のバッチ開始フレーム（p99）

100 フレームを 30 枚ずつのバッチに分けているので、各バッチの最初の 1 枚（計 4 枚）が p99 になります。この 1 枚には、シーンの複製と描画デバイスの作成が含まれます。

修正前は、各バッチの最初の数枚が「Unavailable」でした（3 つ目の tracker の準備待ち）。この数枚は描画はしますが、保存のための読み戻しをしません。新しいデバイスで最初に読み戻すときの準備費用は、数枚後のフレームで払っていました。修正後は、この費用を最初の 1 枚で払います。

つまり、費用が増えたのではなく、別のフレームから開始フレームへ移って重なった、というのが最も可能性の高い説明です。修正前の p95 が高かった（86 / 136 ms → 20 / 17 ms）こととも合います。ただし、フレームごとの内訳は確認していません。最大値は 625 / 911 → 627 / 546 ms で、悪化していません。

バッチごとの複製と作成そのものは、レポートの C2（永続 idle セッション）で除く対象で、今回は変えていません。

### 5.3 プラグインを入れて OFF にしたときの費用

このハーネスでは結論が出ませんでした。`hooks-off`（フックあり、キャッシュ OFF）と `no-hooks`（フックを外した状態）を比べると、4 回ともフックありの方が速く出ています。これは実行順（フック解除後の JIT 再コンパイルなど）の影響で、フックの費用ではありません。

参考値として、`off` モードでの `Update` 全体と本体部分の差（フックの前後処理）は p50 で約 0.003 ms でした。

## 6. 安全性の確認

修正後の commit で CI を 2 回実行し、2 回とも全ジョブが成功しました。次の確認を含みます。

- **画素の一致**：WARP で 100 フレームが画素単位で一致。非待機 readback、ズーム・パン、奇数寸法、透明度のケースも含む。
- **GPU 保持**：8 フレームの画素一致、使用中の追い出し、表示範囲変更・編集・消去での無効化、ソース破棄。
- **キャッシュの無効化**：編集・取消・やり直し、ネストしたシーン、同じメタデータでのファイル差替え、素材の欠落、口パクの一時的な除外。

- **idle**：キャンセル済みのジョブは確定に到達しない。GPU キャプチャ中のキャンセルと消去では、完成した画素を採用しない。

## 9. 追加：保存するフレームの二重描画をやめた（F2・B1、プレビューのみ）

### 9.1 変更

保存するプレビューのフレームは、これまで 2 回描かれていました。

1. 保存（読み戻し）用に、表示サイズのビットマップへ描く。
2. プレイヤーの `Draw` が、ホストの command list からもう一度描く。エフェクト・文字・動画テクスチャの合成を、もう一度評価します。

今回の変更で、1 のビットマップをそのまま表示にも使うようにしました。

- **表示の差し替え**：hit と同じ 1:1 の command list（`UploadPreview` と共通の `RecordPreviewImage`）で、ソースの出力を差し替えます。プレイヤーの `Draw` は合成を評価し直さず、コピーするだけになります。
- **ホスト出力の保持**：ホスト自身の出力は、ホストの disposer に残したままにします。
- **表示条件が変わったとき**：プレイヤーが描く直前の表示条件（ズーム・パン・ウィンドウサイズ）が、描いたときの条件と違う場合、ホストの出力に戻します（`ShowHostOutputIfViewChanged`）。
- **次の Update が hit のとき**：残しておいたホスト出力は、その場で解放します。
- **GPU メモリ**：表示中のビットマップ（1 フレーム分）は、復元フレームと同じく計上します。GPU 保持の対象にはしません。
- **対象外**：書出しキャッシュと idle の経路は変えていません。書出しは、YMM4 がプレビュー以外の倍率で出力を描くかをこの環境で確認できないためです。idle は、もともと 1 回しか描いていないためです。

commit：`3bf001e`（実装）、`8078e9e`・`22b63d6`（計測）。

### 9.2 測り方

- 同じ CI 実行の中で、テスト用の切り替え `DrawOnce` を使い、「1 回描画」と「2 回描画（従来）」を 2 組、交互に測りました。ランナーの速さの差が結論に入りません。
- 各パスは空のキャッシュから始め、全フレームを保存対象にします。
- **ペース付き（paced）**：各フレームの後に、計測の外で GPU の完了を待ちます（イベントクエリ）。「GPU がフレーム間隔内に終わる」状態に相当し、どちらの方式も全フレームを保存できます。
- **2 つの時間**
  - 描画スレッドの時間（`frame` p50 など）
  - 壁時計の 1 フレームあたり時間：描画スレッドの時間に GPU の完了待ちを足したもの。WARP では GPU の処理も CPU で行うため、GPU の仕事量がここに出ます。

### 10.2 変更

**製品コード**（commit `55ec3e4`・`cf7f4e1`・`5a3f222`）

1. **読み戻しを 3 本まで並べる**
   - これまで：1 つのソースで GPU からの読み戻しは 1 本ずつでした。前の読み戻しが終わっていないフレームは、保存を見送っていました。
   - 変更後：3 本まで同時に待てます。見送るのは 3 本とも使用中のときだけです。
   - 1 回の Update で完了させるのは、従来どおり最大 1 本です。描画スレッドの 1 フレームあたりの仕事は増えません。
2. **テクスチャを使い回す**
   - これまで：保存する 1 フレームごとに、8 MB のテクスチャを 2 枚（描画先と読み戻し用）作って捨てていました。
   - 変更後：ソースごとにプールして使い回します。プール中のテクスチャも GPU のメモリ予算に計上します。idle のソースは、別のプールを持ちます。
3. **表示用の command list を使い回す**：1 回描画の表示用 command list を、毎フレーム作り直していました。変更後は、プールしたテクスチャごとに、表示条件が同じ間は同じ command list を使います。
4. **直前に表示したテクスチャへすぐ描かない**
   - これまで：表示を終えたテクスチャを、次のフレームですぐ描画先にしていました。GPU がまだそのテクスチャからコピーしている間、WARP では描画スレッドが待たされます。
   - 変更後：テクスチャを古い順に回し、少なくとも 2 枚を交互に使います。
5. **idle の作業スレッドと描画器を使い回す**
   - これまで：idle はバッチ（30 フレーム）ごとに、シーンの複製、tracker の複製、描画デバイスを作り直していました。
   - 変更後：1 本の作業スレッドがこれらを持ち続けます。モデルとファイル検証の状態が変わらない間は、次のバッチでも使います。
   - 解放するとき：2 秒間仕事がないとき、idle を OFF にしたとき、エラーのとき。

**計測側だけの変更**（製品の動作は変えていません）

- **各パスの前に GC**：前のパスで作ったフレームが、次のパスの途中で回収されたり、ページアウトされたりしないようにします。
- **パスごとの出力を追加**：GC の停止時間、ワーキングセット、プールのバイト数、テクスチャの作成数、見送り数。
- **組の数**：1 回描画と 2 回描画の組を 3 組に増やしました。順番は 1・2、2・1、1・2 です。
- **自動チェック**：次をテストで確かめます。
  - 1 パスで作るテクスチャは 8 枚以下。
  - ペース付きのパスでは全フレームを保存する。
  - idle の連続したバッチでは、描画器は 1 つ。

1 回描画 −（引く）2 回描画の差です。プラスは 1 回描画の方が遅いことを示します。直す前は §9 の 1 回の実行（2 組）、直した後は `cf7f4e1`・`5a3f222` の 4 回の実行（12 組）の値です。

| 場面 | 条件 | 直す前 | 直した後：中央値 | 直した後：範囲 |
| --- | --- | ---: | ---: | ---: |
| base | ペースなし、描画スレッド p50 | +0.98 ms | +0.64 ms | −0.90〜+2.93 ms |
| base | ペース付き、描画スレッド p50 | +0.12 ms | −0.03 ms | −0.30〜+0.34 ms |
| base | ペース付き、GPU 込み | +2.53 ms | +0.69 ms | −5.45〜+4.19 ms |
| files24 | ペースなし、描画スレッド p50 | −0.29 ms | +0.48 ms | +0.22〜+2.79 ms |
| files24 | ペース付き、描画スレッド p50 | −0.11 ms | −0.12 ms | −0.99〜+1.15 ms |
| files24 | ペース付き、GPU 込み | −0.13 ms | −0.11 ms | −0.42〜+2.99 ms |

- **ペース付き**：GPU がフレーム間隔内に終わる状態です。描画スレッドの時間に差はありません。
- **ペースなし（フレームを間を空けずに続けて描く）**：1 回描画の方が 0.5〜0.6 ms（中央値）遅いままです。files24 では 12 組すべてで遅く出ました。30 fps の 1 フレーム枠（33.3 ms）の約 1.5% です。
- **原因の見立て**
  - 1 回描画の表示は、1920×1080（8 MB）の全面をコピーします。2 回描画では、ホストが図形と文字の小さな範囲だけを描き直します。
  - WARP では、このコピーを描画スレッドと同じ 2 コアの CPU で行います。そのため、間を空けずに続けて描くと、描画スレッドと取り合います。
- **実 GPU での見込み**：RTX 3060 で全面 1 枚のコピーは 0.1 ms 未満と見込みます。未計測です。

**今回入れなかった対策**：コピーを、描いた内容の範囲（Direct2D が返す画像の範囲）だけに絞る方法です。範囲の外は黒い背景で、プレイヤーがすでに描いている色と同じです。

- **入れなかった理由**
  - Direct2D が返す範囲が、文字のはみ出しやアンチエイリアスの端まで必ず含むことを、この環境では確かめきれません。
  - 外れた場合、プレビューで端が欠けて見えます。
  - 効果が出るのは、ソフトウェア描画か性能の低い GPU だけです。
- **入れるなら**：文字・回転・ブラーなどで、画素の一致を確かめるテストを先に足してからにします。
