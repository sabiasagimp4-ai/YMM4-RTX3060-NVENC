2026-10-03。前回の調査（[ISSUE_REVIEW_2026-10-03.md](ISSUE_REVIEW_2026-10-03.md)）以降に入れた VRAM の自動配分・RTX 3060 以外の NVIDIA GPU への対応を含め、製品コード（C# 約 9,900 行、C++ 約 3,600 行）を全部読み直した。見つけたものは直し、検査を足した。

### 手元の計測（R3）

保存庫だけを取り出し、RAM に 1,000 件ある状態で 6,000 キーの照会を 200 回繰り返した（Linux、.NET 10）。

| | 照会 1 回の時間 | 照会 1 回の確保 |
| --- | --- | --- |
| 直す前（大文字のキー、1 文字ずつの検査） | 2.4 ms | 1,072 KiB |
| 直した後（小文字のキー、一括の検査） | 0.66 ms | 0 KiB |

この時間はすべて保存庫のロックの中で、描画スレッドの読み込みはその間待つ。R2 で、変化が無い間はこの照会自体を省く。

## 2. 確かめて、問題が無かったもの

| 疑い | 結果 |
| --- | --- |
| VRAM の自動配分のロック順（`cacheGate` → 配分のロック）が逆転してデッドロックする | 配分側は `cacheGate` を取らず、予算の読み書きは lock-free。保持フレームの解放は描画スレッドが次の Update で行う |
| 予算を下げても、YMM4 が止まっている間は保持フレームが VRAM に残る | 仕様どおり（解放は次の描画）。他スレッドから D2D の資源を解放すると、描画中のコンテキストと競合し得るため変えない。止まっている間は Windows が VRAM からシステムメモリへ退避できる |
| NVENC の非同期エンコードで入力テクスチャを使い回して壊す | スロットごとに専用の入力テクスチャがあり、4 フレーム前の完了を待ってから同じスロットを使う |
| MP4 の索引が 4 GiB を超えると壊れる | 4 GiB を超える位置があれば `co64` を使っている |
| 出力設定のビットレートを 1 文字入力するたびに重い処理が走る | 設定ファイルの保存と、値が同じなら即座に戻る適用処理だけ |
| 外部プラグインの信頼設定を変えずに保存しても、全トラッカーが記述し直す | 同じ集合なら世代を進めない |

## 3. 直していないもの

| 内容 | 理由 |
| --- | --- |
| 取消でないのに YMM4 から届いたフレーム数が合わないとき、出力は無言でファイルを作らない（前回 §4.3） | YMM4 は描画中の例外でも出力の後始末（Dispose）を呼ぶ。そこで例外を投げると、本来の例外を隠してしまう。本体の範囲の計算はプラグインと同じことを確認済みで、起きる条件は限られる |
| 検証できない場所の素材（OneDrive・exFAT・ネットワーク・4 GiB 超）を使うフレームはキャッシュしない（前回 #3） | 安全性の前提（内容の指紋）を変える設計判断が要る |
| 色空間を書いていない（前回 #5） | NVIDIA の実機でしか確かめられない。手順は [RTX3060_HARDWARE_CHECK.md](../RTX3060_HARDWARE_CHECK.md) |
| 再生中・指紋計算中は素材を他のアプリから上書きできない（前回 #11） | 上書きの検出の前提。指紋計算をファイルごとに開閉する変更は別に行う |
| 停止中の先読みはツールを閉じると止まる（前回 #8） | 先読みは YMM4 の処理中の状態（`AsyncAwaitStatus`）をツールから受け取る。ツールなしで動かすには本体の別の状態を読む必要がある。文言で明示した |
| 停止中の先読みは YMM4 が背面でも動く | After Effects と同じ考え方とした（前回と同じ） |
| 手動の VRAM 上限は、搭載 VRAM より大きくできる | 手動は利用者の指定を優先する。自動（既定）は搭載 VRAM の 1/4 まで |

## 4. CI

実際の YMM4 Lite 4.56.1.0 と WARP（ソフトウェア描画）で確かめた。

| run | commit | 結果 |
| --- | --- | --- |
| [37115722509](https://github.com/sabiasagimp4-ai/YMM4-RTX3060-NVENC/actions/runs/37115722509) | `adaa577` | 失敗。新しい検査（出力の保存、キャッシュバーのキー、保存庫）は通った。既存の性能検査で、読み戻し用のテクスチャを保存 100 枚に対して 100 回作っていた（使い回しの検査の上限は 8） |
| [37116045839](https://github.com/sabiasagimp4-ai/YMM4-RTX3060-NVENC/actions/runs/37116045839) | `a2ed0fb` | 成功（全ジョブ） |

失敗の原因は R7 の最初の実装だった。プールから取り出したテクスチャと描画先のデバイスを、`GetDevice` のポインターで比べていた。WARP では同じデバイスでも一致せず、毎回プールを捨てていた。比較をやめ、描画か読み戻しが実際に失敗したときにプールを作り直す方式にした（`a2ed0fb`）。作り直した後は、同じ検査でテクスチャの作成は 1 回になった（上限 8）。

`a2ed0fb` での主な出力：

- `Export store: 10 frames stored without waiting for the GPU (the last on disposal), restored by a second export pixel for pixel OK`
- `Cache bar keys: equal to the captures' keys in any frame order, cached per segment, stamp follows edits OK`
- `Cache store restart: the disk LRU follows the records' last use (writes and reads), not file name order.`（Windows と Linux）
- `Cache store: requests do not wait while the disk index loads.`（Windows と Linux）
- 既存の検査：100 フレームの画素一致、GPU 保持、プレビューの保存と再生、停止中の先読み、出力の途中ファイル削除、設定の保存、NVENC のネイティブ不変条件（すべて成功）

性能の数値は WARP・論理 CPU 2 の値で、RTX の値ではない。今回の変更の多くはロックを握る時間と確保の削減で、この環境では差が測定の揺れに埋もれる。R3 の数値は手元の計測（§1）。
