# 立ち絵の口パクとキャッシュ（調査、2026-10-04）

立ち絵（口パク）が映るフレームは、現在キャッシュせず毎回通常描画している。対象にできるかを、YMM4 Lite 4.56.1.0 のコードを読み、実ホスト（GitHub Actions の Windows、WARP）で実験して調べた。実験のコードは一時的に入れて戻した（`efe98ac` に残る）。

## 1. 結論

- **対象にできる。** 口パクの音量は、同じボイスなら毎回・別のプロセスでもビット単位で同じ値になる。書き出し・再生・シーク・逆再生・ソースの作り直しのどれでも、絵は書き出しと一致した。
- 絵が変わるのは、音量の計算が待ち時間内に終わらず、YMM4 が「無音」として口を閉じて描いた場合だけ。その時に返す値は計算結果と違うので、描いた後に確実に見分けられる。そのフレームを保存しなければよい。
- 作業は、キーに足すもの（部品ファイル、PSD の目パチ・口パク設定、既定のまばたき）と、「音量が本物か」の完成判定。
- 調査の途中で、立ち絵より影響の大きい問題が見つかった（5 章）。YMM4 の既定の設定では、セリフが 200 個（3 秒ずつなら会話 10 分）ほどになると、プロジェクト全体がキャッシュの対象外になる。

## 2. YMM4 の口パクの仕組み（4.56.1.0）

### 2.1 どのボイスで口を動かすか

`TimelineSource` が、フレームごとに次のように選んで立ち絵へ渡す。

- 対象は、そのフレームにある表情アイテムとボイスアイテムのうち、立ち絵と同じキャラクターのもの。非表示のアイテムと非表示のレイヤーは除く。
- 口パクに使うボイスは、レイヤーが最も大きいボイス。
- 表情は、選んだもの全部をレイヤーの大きい順に渡す。

どれもフレームに重なるアイテムなので、現在のキーに入っている。

### 2.2 音量

- ボイスが変わると、立ち絵の描画ソースごとに別スレッドで計算を始める。プロセス全体で同時に計算できるのは 2 つまで。
- 計算の中身は次のとおり。
  - ボイスの音声を 48 kHz で読む。再生速度と開始位置は掛ける。音量・エコー・音声エフェクトは掛けない。ボイスのアップサンプリング設定に従う。
  - 各フレームを中心に、キャラクターの「なめらかさ」（`MouseSmooth`、既定 4）フレーム分の二乗平均平方根を取る。
  - 先頭のフレームから順に公開する。
- 描画は、そのフレームの値が公開されるまで待つ。待ち時間の上限は次のとおり。

| 状況 | 上限 |
| --- | --- |
| 動画出力 | max(30 秒, ボイスの長さ + 30 秒) |
| それ以外（プレビューなど） | 30 秒 |
| Dispatcher のあるスレッド | 2.5 秒 |

- 上限を超えると、ログに書いて無音（0）で描く。そのボイスの計算が終わるまでは、以後のフレームも待たない。公開済みならその値、未公開なら 0 になる。
- ボイスがないフレームは -1。「喋っていないときは隠す」に使う。

### 2.3 母音の口

- 口の形は、音声合成エンジンが返す発音か、なければ Rhubarb Lip Sync で解析した結果（`LipSyncFrames`）を使う。どちらもプロジェクトに保存され、キーに入る。
- Rhubarb の解析はボイス作成の後に非同期で行う。終わると `LipSyncFrames` が変わり、アイテムの変更として通知される。

### 2.4 立ち絵プラグイン

| 種類 | 音量の使い方 | ほかに読むもの |
| --- | --- | --- |
| 動く立ち絵（AnimationTachie） | 口の部品の番号 = floor(部品数 × 音量 × 10 × 感度 / 100)。母音優先で `mouth.a.png` があれば母音の部品 | 番号付き部品（`mouth.0.png` …）があるか（部品のパスが変わるまで数え直さない）、部品ごとの `.ini`（重ね方・不透明度・置き場所）、動画の部品 |
| PSD 立ち絵 | 口の割合 = 音量 × 10 × 感度 / 100 を 0〜1 に収めた値 → 口のレイヤーの番号 | `<PSD名>-ymm.json`（起動中に一度だけ読み、以後は YMM4 の画面での編集を共有のオブジェクトで受ける）、PSD ファイル（パスが変わるまで読み直さない） |
| シンプル立ち絵 | 喋っているか（-1 かどうか）だけ | 表情の画像・動画 |

- 動く立ち絵の `.ini` は、値のない項目を前に読んだ部品の値のまま残す。部品が切り替わる順番で結果が変わり得る（YMM4 側の挙動）。番号付き部品に `.ini` がある場合は、対象外にするのが安全。
- PSD 立ち絵は、表示するレイヤーが変わるたびに、表示中の全レイヤーを GPU へ送り直して合成し直す。

### 2.5 まばたき

まばたきの開始と間隔を設定しないとき（既定）は、5〜10 秒を乱数で決める。種は素材フォルダー（PSD ならファイル）のパスの `string.GetHashCode()` で、これは .NET が起動ごとに変える。乱数そのものは種から決まるので、同じプロセスの中ならプラグインが同じ計算をして正確に求められる。

## 3. 実験の結果

動く立ち絵（目 3 枚、口 4 枚、母音 5 枚）と、6 秒の音声（24 kHz）で調べた。

### 3.1 音量の計算

| 音声 | 計算時間 | 2 回目と同じ | 別プロセスと同じ |
| --- | --- | --- | --- |
| 5 秒・24 kHz | 323 ms（初回 1336 ms） | 同じ | 同じ |
| 60 秒・24 kHz | 907 ms（実時間の 66 倍） | 同じ | 同じ |
| 600 秒・16 kHz | 8.1 秒（75 倍） | 同じ | — |
| 5 秒・48 kHz | 35 ms（142 倍） | 同じ | — |

- アップサンプリングの方式によって値はわずかに変わる（24 kHz の音声で最大 0.0007）。この設定は、すでにキーに入っている。
- なめらかさを変えると値が変わる。キャラクターの設定なので、キーに入っている。

### 3.2 描き方による違い

360 フレームを書き出しの絵と比べた。

| 描き方 | 書き出しと同じ絵 | 音量の待ち（最大） | 1 フレームの Update |
| --- | --- | --- | --- |
| 書き出し、順番に | 360 / 360 | 7 ms | 1.0 ms |
| 再生、順番に | 360 / 360 | 5 ms | 0.5 ms |
| 一時停止、ばらばらの順（シーク） | 360 / 360 | 141 ms | 24.6 ms |
| フレームごとにソースを作り直す | 24 / 24 | 93 ms | 49.8 ms |
| 再生、逆順 | 360 / 360 | 96 ms | 0.6 ms |

- どのフレームも、音量は計算結果どおり（本物）だった。
- シークすると、そのボイスの音量を先頭から計算し直すので遅くなる。キャッシュがあれば、この待ちもなくなる。

### 3.3 時間切れ

同時に計算できる 2 つの枠を実験側で占有して、計算を止めた。

| スレッド | 結果 |
| --- | --- |
| Dispatcher あり | 2.5 秒待ってから無音で描いた。口が閉じ、書き出しと違う絵になった。続く 5 フレームは待たずに無音で描き、全部違う絵だった。計算が終わった後は、正しい絵に戻った |
| Dispatcher なし（YMM4 のプレビューと同じ） | 占有を解くまで 3 秒待ち、正しい絵を描いた。プレビューが止まる |

- 時間切れのフレームはすべて「本物でない」と判定でき、本物と判定したフレームはすべて書き出しと同じだった。
- YMM4 のプレビューは Dispatcher のないスレッドで描く。描画の途中で Dispatcher ができることもなかった。普段は 30 秒まで待つので、時間切れはまれ。

### 3.4 部品とまばたきを事前に計算できるか

| 項目 | 結果 |
| --- | --- |
| まばたきの開始・間隔 | プラグイン側の計算が YMM4 の値と一致 |
| 目の部品 | 359 / 360 フレームで予測どおり |
| 口の部品（音量から） | 359 / 360 フレームで予測どおり |
| 母音の口（`LipSyncFrames` から） | 175 / 180 フレームで予測どおり |
| 別プロセスでのまばたき | 文字列ハッシュが変わり、開始・間隔がずれた（9.9 秒 / 5.2 秒 → 8.4 秒 / 8.1 秒） |

予測が外れた残りの数フレームは、記録の取り方の問題か予測のずれかを、まだ切り分けていない。

### 3.5 PSD 立ち絵の重さ

1200×2000、38 レイヤー（表示 33）、21 MB の PSD で、目と口のアニメーションを設定して測った。

- 書き出し（順番に）では、ボイスの 180 フレームのうち 52 フレームで合成し直した。合成し直すフレームの Update は 12.3 ms、それ以外は 0.9 ms。
- シークでは 131 / 210 フレームで合成し直し、Update は平均 17.2 ms。
- 絵は、再生でもシークでも書き出しと同じだった（210 / 210）。

これは WARP（CPU で描画）での値で、実 GPU では違う。レイヤーが多い実際の PSD ほど重くなる。

## 4. キャッシュの対象にする方法（設計案）

### 4.1 キーに入れるもの

| 入力 | 現在のキー | 対応 |
| --- | --- | --- |
| 立ち絵・ボイス・表情アイテム、キャラクターの設定、fps、アップサンプリング設定 | 入っている | そのまま |
| ボイスの音声の中身 | 入っている | そのまま（音声は決定的） |
| 部品ファイル、PSD ファイル | 立ち絵の分は入れていない | 依存に入れる |
| 番号付き部品・母音の部品があるか、部品の `.ini` | なし | 連番画像と同じく、最初に見た一覧と比べる。変わったら再起動まで通常描画 |
| PSD の目パチ・口パク設定 | なし | 共有オブジェクトの内容をキーに入れ、変更通知で記述し直す |
| 既定のまばたき | なし | 同じ計算をして、フレームごとの目の状態をキーに入れる。目を開けているフレームは、再起動後も再利用できる |

### 4.2 完成判定

`TachieSource.ReadVolumeAfterRequiredWait` の後で、返した値を確かめる。

- ボイスの外なら -1 であること。
- ボイスの中なら、その値が計算結果と一致すること。
- 一致しない、計算の失敗・取消などなら、そのフレーム（入れ子のシーンなら外側も）を保存しない。

既存の、動画のデコードの完成判定と同じ仕組みに載る。外部の立ち絵プラグインは、ほかの外部プラグインと同じく対象外のまま。

### 4.3 停止中の先読み

- 音量の計算枠はプロセス全体で 2 つしかない。先読みが計算を始めると、プレビュー側を待たせ得る（最大 30 秒）。そこで、プレビューが計算中でないときだけ、立ち絵のフレームを先読みする。
- 先読みはモデルから複製したシーンで描く。複製にはボイスの音声ファイルのパスがない（JSON に入らない）。複製へライブのボイスのファイルを渡す必要がある。キーはライブと一致することを確認した。

### 4.4 順序

1. シンプル立ち絵：音量は「喋っているか」だけなので小さい作業で済む。
2. 動く立ち絵。
3. PSD 立ち絵：設定ファイルの扱いが要る。

## 5. 調査で見つかった、立ち絵以外の問題

### 5.1 ボイスのキャッシュでプロジェクト全体が対象外になる（重大）

- YMM4 の設定「ボイスのキャッシュをプロジェクトに保存する」（`IsProjectVoiceCacheEnabled`）は、既定で ON。一部のエンジン（Google、Azure、OpenAI など）は、設定によらず必ず保存する。
- ON だと、ボイスの音声（WAV を Brotli で圧縮したもの）が各ボイスアイテムに入る。描画キャッシュは編集のたびにプロジェクト全体を記述するので、その中にも全部入る。

3 秒のボイスでの実測。

| ボイス | 記述の大きさ | 結果 |
| --- | --- | --- |
| 50 個（ボイスキャッシュあり、24 kHz） | 5.6 MB | 対象 |
| 200 個（ボイスキャッシュあり） | 1600 万文字を超える | プロジェクト全体が対象外 |
| 200 個（ボイスキャッシュなし） | 1.0 MB | 対象 |

- 1 秒あたりの大きさ（base64 の文字数）は、16 kHz で約 28,000、24 kHz で約 40,000、48 kHz で約 75,000。
- 直し方：記述ではボイスキャッシュの中身を、そのハッシュ（同じ配列は一度だけ計算）に置き換える。キーの正しさは変わらない（音声の中身が変われば値も変わる）。

### 5.2 ボイスの一時ファイル（問題なし）

YMM4 はボイスを、毎回ランダムな名前の一時ファイルに書き出す。起動するたび、複製するたびに名前が変わる。キーと停止中の先読みへの影響を疑ったが、ライブと複製のキーは一致した。問題はなかった。

## 6. ほかに対応していないもの（2026-10-04 時点）

### 6.1 できるが、まだ対象にしていないもの

| 対象 | 必要な作業 |
| --- | --- |
| ボイスのキャッシュが多いプロジェクト（5.1） | ボイスキャッシュをハッシュで記述する |
| 立ち絵（3 種） | 本書の 4 章 |
| 同じレイヤーで重なるアイテムの並び順 | キーに入っていない。並べ替えると古い絵が出得る（PR #4 の計測で確認）。重なる区間の並び順をキーに入れる |
| DirectShow で読む動画 | Harmony で読込処理に確認を差し込めない。別の確認方法 |
| Community の LUT・グラデーションマップ | 使うファイルを YMM4 に報告しない。設定値からファイルを拾う |
| Community のグループ制御・Container・シーンのブラシ | ほかのアイテムやシーンを描く。依存の範囲を広げる |
| Community の未読の処理（8 種） | コードを読んで判断 |
| MIDI の音声 | SoundFont と設定をキーに入れる |
| 確認できない場所の素材（OneDrive の同期フォルダー、exFAT、ネットワーク、4 GiB 超） | 指紋の方式を変える |

### 6.2 設計上、自動では対象にできないもの

未確認の外部プラグインのコード（設定で「信頼」すれば対象）、OpenFX・VST3、残像・モーションブラー、文字の「ランダム」順の表示、インターネット上・クラウドの「オンラインのみ」のファイル。理由は [AUTOMATIC_COVERAGE_2026-10-03.md](AUTOMATIC_COVERAGE_2026-10-03.md)。
