## 先に直す・分けるもの

### 1. 公開版にある不具合の修正が、積み重ねの最後と途中に入っている（分けて先に出す）

- **PR #13 の `RestoreHostOutputBeforeUpdate`**: 保存するフレームを 1 回だけ描く仕組み（2026-10-02 の 1 回描画）で、描いた画を表示に差し替えた後、次に YMM4 が描くとき YMM4 は差し替えた方だけを解放し、元の出力（command list）は描画器を閉じるまで残っていた。キャッシュを有効にして初回再生するとフレームごとに 1 つずつ溜まる。v0.2.0-preview.1／2 に入っている。
- **PR #10 の `FrameRenderModelComparison`**: 記述には、ランダム移動などがあると、そのオブジェクトの同一性（`identity://…`）がプロジェクト全体の資源の一覧に入る。複製では必ず違う値になるので、`main` では、ランダム系がどこか 1 つでもあるプロジェクトでは、ランダムと関係ないフレームまで停止中の先読みが「複製と一致しない」で全部飛ばされていた。PR #10 は比較の時だけ同一性の値を伏せ、フレームのキーは今までどおり比べる。正しい直し方。

どちらも高速化とは独立した修正なので、`main` からの小さな PR に分け、検査ごと先に入れて preview.3 で出すのがよい。

### 2. 立ち絵のあるシーンでは、停止中の先読みが全部止まる（PR #12・#13）

`AnimationTachieDependencies.ContainsNative`／`PsdTachieDependencies.ContainsNative` が、ルートのタイムラインに動く立ち絵・PSD 立ち絵が 1 つでもあれば、そのシーンの全フレームを先読みしない（立ち絵が映らないフレームも含む）。理由（口パクの計算枠 2 つを再生に残す）は妥当だが、範囲が広すぎる。

- 少なくとも、立ち絵が映らないフレームは今までどおり先読みする（フレームごとに判定する）。
- 立ち絵のフレームも、プレビューが口パクを計算していない時（計算枠が空いている時）だけ描く案を検討する。
- 立ち絵のキーに足した `animation-blink-session://…`・`psd-blink-session://…` は `identity://` で始まらないので、`FrameRenderModelComparison` では伏せられない。先読みを立ち絵のシーンでも動かすなら、これも比較の対象から外す（フレームのキーの比較は残す）。

ゆっくり動画は立ち絵がほぼ全区間に映るので、今の実害は「立ち絵の区間が先読みされない」ことで、2 回目の再生でキャッシュが効くこと自体は大きな改善。マージを止めるほどではないが、次に直す。

### 3. CI に、固定の commit を測る手順が 8 つ常に入っている

`cache-development.yml` の「before／after」の計測（`git fetch origin <40 桁の SHA>` と `git worktree`）が、毎回の CI で動く。

- これらの commit は `codex/*` のブランチにしかない。squash でマージする、またはブランチを消すと取得できなくなり、`main` の CI が赤くなる。
- 毎回、過去の版を測り直すので時間もかかる（今は Windows のジョブが約 11 分で、上限は 30 分）。

マージの前に、計測の手順は `workflow_dispatch` の入力（例: `measure_baselines`）で選んだ時だけ動くようにする。検査（`--psd-tachie-check` など）は常に動かしてよい。

## 直した方がよい（中程度）

### 4. 立ち絵のフレームを出すたびの確認が重くなり得る（PR #12・#13）

- 動く立ち絵の `SafeSource` は、立ち絵が映るフレームの Update のたびに（キャッシュから出す時も）、部品のフォルダーを `Directory.EnumerateFiles` で全部読む。保存の直前（`StillCurrent`）でも同じことをする。CI の部品は少ないが、実際の立ち絵（部品のフォルダーに数百枚）では 1 フレームあたり数 ms になり得て、キャッシュの効果を削る。
- PSD 立ち絵は、検証のたび（`KeyCapture.Validate` からも）に共有設定を JSON にし直す。`Verified` は呼ばれるたびに `AppDomain.GetAssemblies()` を作る。
- PSD の読込済みのバイト列の SHA-256 は、読み込んだファイルごとに 1 回だが、描画スレッドで行う。数十〜数百 MB の PSD では、最初のフレームで目に見える止まりになる。

実際の大きさの立ち絵（部品数百枚、PSD 100 MB 程度）で、2 回目の再生の 1 フレームの時間を測ってから判断する。重ければ、フォルダーの更新時刻で一覧の再読込を省く、設定の JSON を変更通知の世代で使い回す、ハッシュを背景で先に計算する、などで軽くできる。

### 5. 立ち絵のフレームは起動し直すと使えない（PR #12・#13、設計どおり）

まばたきの乱数の種が起動ごとに変わるため、立ち絵のフレームのキーに起動ごとの値を入れている。正しいが、起動し直すたびに立ち絵の区間は全部描き直しになり、ディスクには使えない記録が溜まる（容量の上限で古い順に消える）。計画の本来の案（YMM4 と同じまばたきの計算をして、目の部品の番号をキーに入れる）を、次の段階として残しておく。

### 6. GPU の自動配分が大きい（PR #9）

- 上限が「搭載 VRAM の 1/4」から「搭載 VRAM 全部（最大 8 GiB）」になった。OS の予算と余裕（予算の 1/5 か 1 GiB）で抑えるが、YMM4 自身が急に VRAM を使う場面（出力、重いエフェクト）では、1 秒ごとの調整が追い付くまで足りなくなり得る。上限は搭載量の 1/2 程度から始め、利用者の PC のトレースで広げるのが安全。
- 設定の既定が `-1`（自動）になったが、今の利用者の設定ファイルには 2048 が保存されているので、既存の利用者は広がらない。前の既定のまま（自動・2048）の人は、一度だけ `-1` に移す処理を入れるとよい。

### 新しく見つけた小さな点

- `PsdTachieDependencies.Verified` が `SingleOrDefault` を使うため、同じ名前の `PsdParser`／`YukkuriMovieMaker.Plugin.FileSource.Psd` が 2 つ読み込まれていると例外になる。PSD 立ち絵のキャラクターがいるプロジェクトでは、`KeyDependencyTracker.RebuildSubscriptions` からこの例外が出て、プロジェクト全体が通常描画になる（誤った絵は出ない）。例外ではなく `false` を返す方がよい。
- GPU の上限の下限が 128 MiB から 0 になった。専用の VRAM が小さい（または 0 の）内蔵 GPU では、GPU 保持がほぼ使われなくなる（RAM からの表示は使える）。意図どおりなら、その旨を仕様に書いておく。
- 動く立ち絵の 2 回目の再生は、検査の素材では自身の OFF の 0.69〜0.96 倍で、差が小さい。検査の素材は描画そのものが軽いため。実際の立ち絵で、利用者の PC のトレースで確かめる。
