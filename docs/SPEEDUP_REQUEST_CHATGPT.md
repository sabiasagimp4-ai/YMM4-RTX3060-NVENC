# 高速化の実装の依頼文（ChatGPT 用）

GitHub のリポジトリを読み書きでき、GitHub Actions を動かせる ChatGPT（Codex）へ、この文書の「依頼文」以下をそのまま渡す。ChatGPT は [高速化の実装計画](SPEEDUP_PLAN_2026-10-04.md) の項目を順に実装し、項目ごとに draft PR を出して、最後の形式で報告する。報告は Claude Code へ貼り戻してよい。

---

## 依頼文

あなたは、YMM4（ゆっくりMovieMaker4 Lite）用プラグイン「YMM4-RTX3060-NVENC」の描画キャッシュを速くする実装の担当です。計画はリポジトリの `docs/SPEEDUP_PLAN_2026-10-04.md` にあります。計画を読み、項目ごとに実装・検査・計測・文書の更新までを自分で行い、draft PR にしてください。判断に迷う点は、この依頼文と計画に従い、それでも決まらないときは安全な側（キャッシュしない・通常描画に戻す側）を選んで、報告に書いてください。

### 対象

- リポジトリ: `https://github.com/sabiasagimp4-ai/YMM4-RTX3060-NVENC`
- 起点のブランチ: `claude/ymm4-nvenc-perf-analysis-5h1aik`（この文書を含む commit 以降。`main` に計画と依頼文を足したもの）
- 基準のホスト: YMM4 Lite 4.56.1.0
- 先に読むもの: `docs/SPEEDUP_PLAN_2026-10-04.md`（計画）、`docs/CACHE_BEHAVIOR.md`（今の仕様）、`docs/HOST_CONTRACTS.md`（ホストへの依存の決まり）、`docs/PERFORMANCE_RESULTS_2026-10-02.md`（計測の方法と読み方）、`docs/LIPSYNC_RESEARCH_2026-10-04.md`（2 の調査）

### 進め方

1. 計画の推奨の順番で進める: **1 → 4 → 2a → 6 → 8 → 5 → 2b → 2c**。計画の 3・7・9 はやらない。
2. 1 項目につき 1 本のブランチと 1 つの draft PR にする。
   - ブランチ名: `codex/speedup-<番号>-<短い英語名>`（例: `codex/speedup-1-voice-cache-hash`）
   - 起点: 前の項目の PR がまだマージされていなければ、前の項目のブランチから作る（積み重ね）。マージ済みなら `main` から作る。
   - PR の宛先は `main`。マージは利用者が行う。
3. 各項目の中は、計画の「変更」「検査」「測定と合格基準」の順に進める。まず計測のための変更だけを入れた commit で「前」を測り、次に実装して「後」を測る。
4. CI は `cache-development` を使う。PR を出すと自動で動く（`NVEncVideoWriterPlugin/**`・`tests/**` を変えた場合）。ブランチで手動実行（workflow_dispatch）もできる。
5. 1 項目が終わったら（完了の条件を満たしたら）次へ進む。全部終わるか、続けられない理由ができたら、報告する。

### 守ること

1. `main` へ直接 push しない。PR をマージしない。リリース（タグ、`release` ワークフロー）をしない。force push・ブランチの削除をしない。ほかの人のブランチ（`claude/*`、既存の `codex/*`）へ push しない。
2. 検査を通すために、既存の検査を消す・弱める・飛ばす・無効にすることをしない。検査が間違っていると判断したら、理由を PR と報告に書いてから直す。
3. 画素一致（キャッシュから出した絵が、キャッシュを切った YMM4 自身の描画と 1 画素も違わない）を速さより優先する。確かめられない場合は、そのフレームを保存しない・通常描画に戻す側にする。
4. 結果を推測で書かない。数値は CI の実際の出力から取り、run の URL を添える。CI の Windows ランナー（2 コア、Direct2D は WARP＝ソフトウェア描画）の値を、RTX 3060 の値として書かない。
5. 失敗を「たまたま」と扱わない。再実行は、試験の本体が始まる前の失敗（ダウンロード、ランナーの切断など）か、同じ commit で以前に通っていた場合だけ、1 回まで。2 回目の失敗は本物として調べる。
6. YMM4 の DLL を逆コンパイルして読むのはよい（調査のため）。逆コンパイルしたコードを製品に写さない。YMM4 のバイナリをリポジトリに入れない。
7. 新しくホストのメソッドに Harmony で入る場合（2b の `TachieSource.ReadVolumeAfterRequiredWait` など）は、`docs/HOST_CONTRACTS.md` の手順に従い、ホスト契約（`HostContracts.Rules`）と基準値（`HostBaselines.cs`、`tools/HostFingerprint` で生成）を更新する。契約が合わない版では、その機能を無効にする。
8. 一時的な調査用のコード（プローブ）は入れてよい。commit のメッセージに `(temporary)` と書き、項目を終える前に戻す。結果は文書に残す。
9. commit メッセージは英語で、`feat:`・`fix:`・`test:`・`docs:` などで始める。文書だけの commit には `[skip ci]` を付ける。文書は日本語で、既存の文書と同じ平易な書き方にする。

### 完了の条件（各項目）

- 計画の「検査」を、CI で毎回動く検査として実装した（`tests/CacheChecks`、`tests/HostCacheProbe` などの既存の仕組みに足す）。
- 最後の commit で `cache-development` の全ジョブが成功した。
- 計画の「測定と合格基準」を、前後それぞれ同じ CI ジョブで 2 回ずつ測り、合格基準を満たした（満たさない場合は、その理由と、それでも出す価値があるかを書く）。
- `docs/CACHE_BEHAVIOR.md`（仕様が変わった所）、`docs/SPEEDUP_PLAN_2026-10-04.md`（その項目に「済」と PR の番号を書く）、`docs/SPEEDUP_RESULTS_2026-10.md`（新しく作り、項目ごとに結果を足す）を更新した。
- PR の説明に、変更・検査・前後の数値（run の URL 付き）・計画からの変更点・残った危険を書いた。

### 計画の前提が崩れたとき

- 例: 1 で YMM4 の JSON の設定を取り出せない、2b でまばたきの計算が YMM4 の絵と一致しない、8 で 2 本同時に描くと画素が合わない。
- その項目で計画にある代わりの方法を試す。代わりもだめなら、その項目を止めて理由と分かったことを PR と報告に書き、依存しない次の項目へ進む（1 が止まっても 4・6・8・5 は進められる。2b・2c は 2a の後）。

### 知っておくこと（これまでに分かったこと）

- **ローカルではビルドが通らないことがある**: YMM4 の DLL はリポジトリにない。`bash tools/ci/fetch-ymm4.sh 4.56.1.0 <フォルダー> --top` で取得できるが、最終的な判定は CI で行う。
- **CI の時間制限**: Windows のジョブは 30 分で止まる。新しい検査がハングすると、そのジョブ全体が失われる。たくさんの処理を順に試す検査は、1 件ずつ別スレッド・別の描画デバイスで動かし、時間制限（例: 30 秒）を付ける。
- **同じブランチの CI は新しい方が古い方を取り消す**（`concurrency`）。結果を待っている間に同じブランチへ push しない。
- **ランナーの速さは毎回違う**: 計測は、キャッシュを切った `off` を速度計にして比べる（`docs/PERFORMANCE_RESULTS_2026-10-02.md` の §2）。
- **同梱の Community プラグインのシェーダー**は WPF の `pack://` の URI で読み込まれる。検査のプロセスで描くときは、`System.IO.Packaging.PackUriHelper.UriSchemePack` に触れて URI の形式を登録し、`System.Windows.Application` を作っておく。
- **同一性を種にした乱数**（ランダム移動など）のフレームは、その起動中・そのオブジェクトに限ったキー（Session）になる。停止中の先読みでは、そのフレームだけ実物のシーンを描く描画器で描く（`IdleFramePreRenderer.PrimeBatchFrame`）。8 で描画器を増やすときは、実物のシーンを描く描画器は 1 本だけにする。
- **前のフレームに依存する処理**（残像、モーションブラー、CircularBlur）は対象外。動くアイテムでしか差が出ないので、検査は動くアイテムで行う。
- **停止中の先読みの複製**は記述（JSON）から作る。1 でボイスの中身をハッシュにすると、複製にはライブの配列を渡す必要がある（計画の 1 の 3）。
- **YMM4 は起動中に上書きされた素材の古い内容を表示し得る**。変更を検出した素材は再起動まで通常描画にしている（`HostContent`）。4 でもこの扱いを保つ。

### 報告の形式

項目ごとに次を書く。最後に全体のまとめを書く。

```text
## 項目 <番号>: <名前>
- 状態: 完了 / 一部 / 中止
- ブランチ・PR: <ブランチ名>、<PR の URL>
- 変更: <何をどこで変えたか（3〜6 行）>
- 検査: <足した検査と結果。最後の CI の run の URL>
- 計測（CI、WARP。RTX 3060 の値ではない）:
  | 対象 | 前（2 回） | 後（2 回） | 合格基準 | 判定 |
- 計画からの変更点: <なし / 内容と理由>
- 残った危険・未確認: <内容>
- 利用者の PC で確かめてほしいこと: <手順と見る所（ツールの詳細ログのどの値か）>

## まとめ
- 完了した項目、止めた項目と理由
- マージの順番（積み重ねたブランチの依存）
- 次にやるとよいこと
```
